# Compatibility

English · [中文](compatibility.zh.md)

Harness Forge does not label a whole plugin "supported" or not. It looks at each part of a plugin (a skill, a command, an agent, a hooks file, an MCP server, a code module, a UI surface…) and reports what happens to that part in DSH.

## How a part is judged

Before migration, the state is a prediction from the plugin's files. After migration, it comes from what actually happened:

| Record | When |
|---|---|
| mounted | The part is set up in DSH but has not run yet |
| verified | The part ran in DSH: the hook ran, the tool was called, the skill was loaded, the command was dispatched, the agent ran |
| failed | Setting it up failed, or a run failed; the error is kept |
| run observations | Every later run, success or failure, per signal (the latest one each) |

The workbench turns these, and the gaps found in the files, into one state per part:

| State | Meaning |
|---|---|
| Works | Set up with no known gap. Marked as checked once it has run in DSH |
| Partly works | Set up, but something it uses does not exist in DSH (an event DSH never raises, for example), or some of its runs failed |
| Needs an adapter | DSH has no equivalent, but an adapter can fill the gap: **Fill with AI** ([porting](porting.md)) |
| Not possible | DSH has no equivalent and nothing local can stand in for it |
| Error | Setting it up failed, or every run failed |
| Inactive | The row that serves this kind of part is switched off |

A part served by an installed adapter shows as working, but not as checked until it runs.

### Hook events

Hooks run on these events: `SessionStart`, `UserPromptSubmit`, `UserPromptExpansion`, `PreToolUse`, `PermissionRequest`, `PostToolUse`, `PostToolUseFailure`, `Notification`, `SubagentStart`, `SubagentStop`, `Stop`, `StopFailure`, `PreCompact`, `PostCompact`, `SessionEnd`.

`PreCompact`, `PostCompact`, `Notification` and `StopFailure` are seen after DSH has committed them: their hooks run, but a blocking decision is ignored. Hooks on any other event never run.

Handler types `command`, `http`, `mcp_tool`, `prompt` and `agent` are executed, on the events where Claude Code runs them. Other handler types are reported and stay inert. A plugin's own hook `matcher` is a regular expression the plugin chose; it runs only on short names the host chooses (tool, event and agent names), and the plugin is code you installed and trust anyway.

A command hook reads its input from a file rather than a pipe. The file sits in a private folder in Harness Forge's data folder and is removed as soon as the hook starts; one that cannot be removed is reported in the workbench. On Linux and macOS only you can read it (mode 0600 in a 0700 folder that must not be reached through a symbolic link). Windows has no such modes: there the file relies on the access rules the data folder inherits from your profile folder, which normally only you, administrators and the system can read. That is not owner-only access: Harness Forge sets no access rules of its own there. If the private file cannot be created (for example the folder is not private or not writable), the input goes through a pipe instead. Swapping the file or its folder between Harness Forge's checks and the hook's start would need write access to your own data folder, which already means control of your account. Instruction files have a similar residual on macOS and Windows, which have no `/proc`: there, finding an instruction file's real path and confirming it names the file opened are two separate steps, so another program running on this computer at the same moment that swaps a parent folder for a link between them could redirect a read; Harness Forge accepts this, because refusing would stop instruction files from loading on those systems (on Linux the real path comes from the open file itself).

### MCP server settings

Codex servers, from `config.toml` `[mcp_servers.<name>]` or a Codex plugin's `.mcp.json`, `mcp.json` or manifest `mcpServers`, are read the same way:

| Codex setting | In DSH |
|---|---|
| `command`, `args`, `env`, `cwd`, `url`, `type = "http"` | Honoured; `cwd` is relative to the plugin, `type = "http"` is Streamable HTTP |
| `env_vars`, `bearer_token_env_var`, `http_headers`, `env_http_headers` | Honoured: the named variables are passed on from DSH's environment |
| `enabled = false` | The server is not started; its part says "disabled in the plugin" (or "in config.toml"). This holds for every plugin's servers, Claude Code's too |
| `auth = "chatgpt"` | Not started: it needs ChatGPT sign-in, which DSH cannot provide. Reported as a gap |
| `enabled_tools`, `disabled_tools` | Honoured. Through the capability catalog and for remote servers, filtered tools are not listed. A stdio server mounted directly still lists them, but a call is refused |
| `default_tools_approval_mode`, `tools.<tool>.approval_mode` | `prompt` asks you before each call, as Codex does. `writes` asks before every call, because which tools are read-only is not known in advance. `auto` and `approve` leave the call to DSH's own approval |
| `startup_timeout_sec`, `tool_timeout_sec` | Honoured where DSH can time them; without them, a server has 120 s to start and a call 10 minutes. A remote server's start is not timed |
| `omit_tools_from`, `tools.<tool>.output_token_limit` | Ignored: DSH has neither of the Codex tool surfaces `omit_tools_from` names, and bounds tool output itself |

Codex provides two variables to its plugins' servers: `CODEX_HOME`, which is your Codex folder (`$CODEX_HOME`, else `~/.codex`), and `CODEX_MCP_NODE_PATH`, which is the Node.js Codex bundles. DSH provides the Node.js it runs on instead. A server gets them only when its settings ask for them. If a server's command or arguments use a variable that nothing sets, it is not started. Its part says "needs NAME, which DSH does not provide" instead of failing with an empty program.

As in Claude Code, `${VAR}` and `${VAR:-default}` in a server's `command`, `args`, `env`, `url` and `headers` are replaced by the value as text, so a value expanded into a shell script argument such as `sh -c '… ${VAR} …'` becomes part of that script: the values come from the plugin's author and your own environment, and Harness Forge keeps that meaning rather than quoting them.

A server's DSH name never contains `__`, so a tool name `mcp__<server>__<tool>` belongs to one server only: a name with `__` (for example `app__reports`) has it collapsed to `_` and a short hash appended (`app_reports_4880b6d7`), which keeps it apart from a server named `app_reports`.

A server that failed to start is tried again when the MCP row starts again, not once for every other part of Harness Forge that starts.

### Permission rules

Permission rules and hook `if` conditions match as [Claude Code documents them](https://code.claude.com/docs/en/permissions). A shell rule is compared with a command's own words: redirections (`> out`, `2>&1`, `<<< x`) are set apart, so a deny or ask rule for `Bash(git status)` also catches `git status > out` and `>out git status`. PowerShell commands are read the same way, without case, with PowerShell's default aliases read as their cmdlets on both sides (so `PowerShell(Remove-Item *)` also matches `rm`, `del` and `ri`; deny and ask rules and hook conditions know every alias on every platform, while an allow rule approves an alias only where PowerShell defines it, so on Linux and macOS it approves no native `rm` or `ls`), and with PowerShell's own redirections: `>`, `>>`, the streams `1>`–`6>` and `1>>`–`6>>`, `*>` and `*>>`, the merges `2>&1`…`*>&1` (no file), and `<` (which PowerShell 7 reserves and refuses to run). An allow rule approves the command, not where it writes, as in [Claude Code](https://code.claude.com/docs/en/permissions#redirections). A file the command writes through a redirection needs an `Edit` allow rule for that file. A file it reads from outside the working directory needs a `Read` allow rule. Each shell's null device (`/dev/null` in bash; `$null` in PowerShell; `NUL` on Windows) and descriptor copies such as `2>&1` need nothing. A target with `~`, a glob or an expansion is never approved. Each file a redirection reads or writes gets the same deny, ask and allow rules as a `Read` or `Edit` call on it, and the strictest answer wins: a deny anywhere denies the command, else an ask anywhere asks, else it is allowed only if the command and every file are. A symbolic link is checked both as written and where it leads: a deny or ask rule matching either applies, while an allow (and the exception for reads inside the working directory) needs both to qualify, so a link inside the project cannot open a file outside it. File rules use gitignore patterns: a bare name such as `x` matches at any depth under the working directory, while `./x`, `sub/x` and `/x` match only where they are anchored.

## What is found on this computer

- **Claude Code.** Plugins come from `~/.claude/plugins/installed_plugins.json`, one install per plugin: the newest user-scope one. Installs made for one project (`--scope project`, `--scope local`) load only in that project's sessions in Claude Code, so they are left out of Discover and **Migrate all**; add one by hand (**Add a plugin by path**) to use it everywhere. Whether a plugin is on follows Claude Code's own precedence for `enabledPlugins`, the [highest source that mentions it](https://code.claude.com/docs/en/plugins/loading#find-where-a-plugin-is-enabled): your `~/.claude/settings.json`, then the managed settings files (`managed-settings.json` and `managed-settings.d/*.json` in the system folder). Project settings don't apply to the list, which is not tied to a project. MDM and server-managed policies can't be read.
- **Codex.** The plugins `config.toml` lists under `[plugins]`; `enabled = false` marks one as off.
- **OpenCode.** One inventory per config folder, as [OpenCode loads plugins](https://opencode.ai/docs/plugins/): `.ts`, `.js` and `.mjs` files and package folders right inside `plugins/` (or V1's `plugin/`), and the `plugins` (or V1 `plugin`) entries of `opencode.json(c)`. Local entries are folders resolved from the config file; npm entries are read where OpenCode installed them, the config folder's `node_modules` or the cache `~/.cache/opencode/node_modules`, and one not installed there is skipped. The plugin files of `~/.config/opencode` are your own assets (**OpenCode → user**), each package a plugin of its own. Nothing deeper is searched. Entries that [switch plugins off or on](https://opencode.ai/docs/plugins/#control) (`-<id>`, `*`, `<prefix>.*`, a later id) are applied in order, the global config before a project's. They match a plugin by the id its `Plugin.define({ id })` declares. That id is read from the source without running it: comments, strings and template literals don't count, and it must be a plain string in exactly one declaration. Escapes in it (`\u002e`, `\x2e`, `\n`) are decoded as JavaScript decodes them. A plugin OpenCode switches off is listed as off, and **Migrate all** leaves it out. A plugin's id may be missing, declared twice, computed, or written with an escape JavaScript refuses in a module (such as a legacy octal `\1`). If an entry other than `*` or `-*` could switch it, whether OpenCode runs it can't be told. It is listed as maybe off, with the reason, and **Migrate all** leaves it out too; you can still migrate it on its own. The person's own files are listed as off only when every one is switched off; otherwise only the files OpenCode surely runs are kept. An entry that can't be resolved, such as a `file://` URL with a host, is skipped and named on the **Settings** screen. The other plugins are still listed.
- A plugin switched off in its harness is listed, marked off, and left out of **Migrate all**.

## The ledger

What Harness Forge installed is recorded in `.harness-forge/state.json` of the profile. When part of it can't be read, the file is first kept beside it as `state.json.unreadable-<time>` (never overwritten), then records missing something that can be filled in (the install time) are repaired and the rest of the valid records kept. Records that can't be read are left out, and **Diagnostics** shows a fault naming them and the kept copy. A ledger written by a newer Harness Forge is not read and never written over: Harness Forge starts with nothing installed, every install is refused, and the fault says to upgrade.

## Known gaps

These are the reasons the workbench gives. Each is derived from the plugin's files or from what happened at run time.

| Reason | What it means |
|---|---|
| No equivalent UI | Status lines, themes, workflows, monitors, MCP apps and other UI surfaces have no direct place in DSH. An adapter can rebuild one: **Fill with AI** |
| Events never raised | The hooks file listens to events DSH never raises; those hooks never run. An adapter can sometimes raise them from DSH's own events |
| Cannot block | Hooks on `PreCompact`, `PostCompact`, `Notification`, `StopFailure` run after the fact |
| Handlers inert | Hook handler types the broker does not execute |
| Not mapped | LSP servers, a plugin's `bin/` executables (added to `PATH` by Claude Code), install-time `userConfig` options, and OpenCode plugins a project's `opencode.json` names by npm package (they are not in the project's folder) are listed but not run |
| Hosted connector | Codex app connectors are hosted by OpenAI and only work signed in to ChatGPT or Codex. Not possible locally |
| Experimental runtime | Claude Code mods and OpenCode plugins run on a compatibility layer for their host API; a call outside the supported part fails. Once the code has run successfully this reason is dropped |
| Unknown transport | An MCP server that declares neither a known type nor a command or URL is skipped |
| Needs ChatGPT sign-in | A Codex MCP server with `auth = "chatgpt"` uses your ChatGPT session; DSH has none, so it is not started |
| Output style | See *Output styles* above |
| Setup failed / run failed | The recorded error, word for word |

A plugin that declares no license is fine to use locally. The assessment still records it, because publishing anything derived from it (an adapter, for example) needs a license decision.

Remote MCP servers and hooks that call programs need the network or those programs on your machine; when they are missing, the part fails with that error.

## Plugins from the internet

What **Get plugins** can fetch, by harness. Everything is installed through the same path as a local plugin, so the tables above apply to its parts.

| Harness | Marketplaces | Plugin sources in a marketplace entry | Pasted directly |
| --- | --- | --- | --- |
| Claude Code | `.claude-plugin/marketplace.json` in a git repository (`owner/repo`, git URL, `@ref`/`#ref`), or a `marketplace.json` URL | relative path (including bare names under `metadata.pluginRoot`), `github`, `url` and `git-subdir` over HTTPS (with `ref`, or a full 40-character `sha`, also as `URL#sha`), `npm` (from npm's registry or yours), `archive` (zip over HTTPS, checked against `sha256`). `command` is listed but not installed | a plugin repository or subfolder |
| Codex | `.agents/plugins/marketplace.json` in a git repository | `local`, `url`, `git-subdir`, `npm` | a plugin repository (`.codex-plugin/plugin.json`) |
| OpenCode | (OpenCode has no marketplaces) | none | an npm package (`name`, `name@version`, `@scope/name`) |

A Claude Code marketplace entry also acts as a manifest, following Claude Code's rules: with no `plugin.json`, the entry is the manifest; with one, the entry's `skills`, `commands`, `agents` and `hooks` are added to it unless the entry sets `"strict": false`. Harness Forge writes the combined manifest into its own copy of the plugin, so a marketplace such as `anthropics/skills`, whose entries list skills by path, installs the skills its entries name.

An OpenCode npm plugin runs on the Bun runtime, like an OpenCode code plugin found on disk. Before you confirm, npm doesn't run. Harness Forge reads the package from the registry npm is configured with (`npm_config_registry` or the `registry=` line of `~/.npmrc`, else npm's own registry). It takes an exact version or a tag such as `latest`, not a range, downloads that version's tarball from the registry's own address, and checks it against the registry's sha512 integrity. Per-scope registries and registry sign-in aren't read. The confirmation names the registry and how many dependencies the plugin declares. They're installed from that registry when you confirm, as OpenCode installs plugins, with `npm install --ignore-scripts`. A plugin that depends on a git repository, a URL or a local folder, directly or deeper down, is refused. Once you confirm, npm works out the dependencies with its own configuration and may contact other hosts while it does, such as the hosts your npm settings or a registry redirect name. Harness Forge's check covers the packages recorded in the result: each must be a tarball from that registry, with an integrity. npm is told to record them in lockfile version 3 whatever your npm settings say, and a result Harness Forge can't read that way is refused rather than installed.

### What a source may do before you confirm

Nothing fetched runs before you confirm: no hook, script, git setting or install step of the plugin or its marketplace. What you confirm is what gets installed. If the downloaded files change after you saw them, or an update's revision differs from the one **Check for updates** found, Harness Forge refuses to install them. An update is also refused when the installed copy changed after **Check for updates** compared it, for example because another update was installed in between: check again. A plugin from a marketplace or folder already on this computer is copied too, when you open its confirmation: what you confirm and what gets installed is that copy, so a harness refreshing its marketplace in the meantime changes neither, and the original folder is left as it is.

- **A marketplace names only public HTTPS sources.** Its git entries must use `https://` URLs on public addresses, with redirects not followed. An `archive` is downloaded over HTTPS. An `npm` entry may name only npm's registry or yours. A marketplace cannot point Harness Forge at this computer, your local network, `ssh`, `file:` or other git transports. Sources you paste yourself may use any host and `https`, `http`, `ssh`, `git` or `file`. A redirect, though, even from an address you pasted, must lead to a public address.
- **Without a proxy, each connection goes to the address that was checked.** Harness Forge's own downloads (marketplace files, GitHub archives, npm documents and tarballs) connect to the address it checked. For a marketplace's git URL, git is held to that address too, which needs git 2.37 or later; without a suitable git, GitHub sources come as archives and other hosts are refused.
- **Behind a proxy, only known hosts.** Harness Forge uses the proxy set in `HTTPS_PROXY`, `HTTP_PROXY` or `ALL_PROXY` (an `http://` or `https://` proxy, with a user name and password if needed), and skips the hosts in `NO_PROXY`, as git and npm do. Because the proxy resolves host names, Harness Forge can't tell where a name leads. Through a proxy it therefore reaches only `github.com`, `codeload.github.com`, `api.github.com`, `raw.githubusercontent.com`, `objects.githubusercontent.com`, `registry.npmjs.org`, your configured npm registry, and the hosts of sources you paste yourself. A marketplace entry or a redirect that leads to any other host is refused, with the host named. To install from such a host, paste that source yourself, or add the host to `NO_PROXY` if it can be reached directly. This relies on your proxy: it resolves host names and connects, so Harness Forge trusts its answers for the hosts above. Certificates are still checked against the host's name, also through the proxy. git gets the same route Harness Forge chose (proxy or direct), not its own reading of the proxy variables (a proxy password goes to git through its environment, which needs git 2.31 or later), and follows no HTTP redirect, so a repository that moved has to be pasted at its new address.
- **No links.** Plugins are plain files and folders. An archive that contains a link, a hard link or a device file isn't unpacked, and a plugin copied from a repository or a folder on this computer leaves its links out (the confirmation says which). A plugin folder that is a link, or is reached through one, isn't copied at all.
- **git runs without your git configuration.** It skips your global and system settings, hooks, templates, credential helpers and `GIT_*` variables, and doesn't fetch submodules or LFS files. As a result, private repositories over HTTPS aren't supported. A private repository you paste as an `ssh` URL (`git@host:owner/repo.git`) works with your own SSH keys.
- **Bounded.** Each operation stops after 10 minutes. A download, clone or install also stops once it writes more than the size limit, even if the server ignores the request for a partial clone. A pinned commit is fetched on its own; if the server doesn't allow that, Harness Forge reports it rather than downloading the whole history.

## Workspace trust

A project brings its own parts: `.claude/` and `.mcp.json` for Claude Code, `.codex/` for Codex. Some of them run code on your computer or reach the network the moment a session starts, so, as in Claude Code, they wait until you trust the workspace:

- hooks (`.claude/settings.json`, `settings.local.json`, `.codex/hooks.json`);
- MCP servers from `.mcp.json` and `.codex/config.toml`;
- commands and skills with a `` !`command` `` or ```` ```! ```` line, frontmatter `hooks`, or `allowed-tools`;
- agents with frontmatter `hooks` or `mcpServers`;
- the parts of a settings file that grant: `permissions.allow`, `env`, and `disableAllHooks: false`. Restrictions never wait: its `permissions.deny` and `permissions.ask` rules and `disableAllHooks: true` apply at once, even when the same file also has `allow` rules or `env`.

Plain skills, agents and commands load at once. MCP servers you added yourself for the folder (`claude mcp add --scope local`) are yours and do not wait.

The workspace is the repository root (a worktree's main checkout), or the working directory outside a repository. It is trusted when any of these holds:

- you accepted Claude Code's trust dialog for it: `projects["<workspace>"].hasTrustDialogAccepted` in `~/.claude.json`. Outside a repository, a trusted parent folder covers it, except your home directory, which covers only itself;
- Codex marks it trusted: `[projects."<workspace>"] trust_level = "trusted"` in `~/.codex/config.toml`;
- you trusted it in Harness Forge. Sessions in an untrusted workspace that has such parts show a **Trust this folder?** banner on the Discover and Migrated screens, listing what waits. **Trust this folder** saves the choice for this DSH profile, in `.harness-forge/trust.json` beside the ledger, and mounts the waiting parts in the sessions already open there. **Not now** hides the banner for that workspace for good: it is saved as `dismissed` in the same file, and trusting later ends it. **More → Settings → Trust settings** lists the workspaces you trusted or dismissed, with **Trust this folder** and **Revoke trust**; revoking withdraws the parts that run code from the sessions already open there (its `deny` and `ask` rules stay), and the banner returns. The same is available as the Remote methods `harnessCompat.workspaceTrust({ cwd })`, `harnessCompat.trustWorkspace({ cwd, trusted })` (it returns `{ decision, stillLive }`: parts whose withdrawal failed are still live, and calling it again retries), `harnessCompat.trustDecisions()` and `harnessCompat.dismissTrust({ cwd, dismissed })`.

A project `.mcp.json` server also needs approval, as in Claude Code: `disabledMcpjsonServers` in any settings file always rejects it. When only Claude Code's trust covers the workspace, it needs `enabledMcpjsonServers` or `enableAllProjectMcpServers` too. Those approvals come from `~/.claude.json` or your `~/.claude/settings.json`, and the project's own settings count only once the folder is trusted. Trusting the folder in Harness Forge approves its servers. A server that is not mounted is never started, so none of its environment variables are expanded into its command, headers or URL.

## Commands and skills: arguments, `!` and `@file`

Shell lines (`` !`…` ``, ```` ```! ````) and `@file` references are found in the command or skill as it is written, before any argument goes in. Command output is never scanned again. Three things differ from Claude Code on purpose:

- **Arguments in a shell line are data.** Claude Code pastes the argument text into the command, so an argument like `"; rm -rf ~"` becomes shell syntax. Harness Forge never puts a value into the command text. Each value (an argument or a path variable such as `${CLAUDE_PLUGIN_ROOT}`) goes into an environment variable, `HF_ARG_0`, `HF_ARG_1`, …, and the placeholder is replaced by a reference to it only where that reference is certain to stay plain data. In bash that means unquoted (`"${HF_ARG_0}"`) or inside plain double quotes (`${HF_ARG_0}`). In PowerShell it means outside quotes or inside plain double quotes (`${env:HF_ARG_0}`). A placeholder anywhere else stops that shell line from running, and a `[Harness Forge: this shell command was not run: …]` note takes its place. "Anywhere else" covers single quotes, `$'…'`, here-documents, PowerShell here-strings, backticks, `$(…)`, `${…}`, arithmetic (`((…))`, `let`, `$[…]`), `[[ … ]]` and comments. The reference must also be an argument of a simple command, and the line runs only if it is. A placeholder may not be the command itself (the first word of a line or after `;`, `&`, `&&`, `||`, `|`, `(`, `{`, `if`, `then`, `do`, `else`, `!` and the like), part of an assignment (`X=$1 cmd`), or an argument of a command that runs, evaluates or names what it is given: in bash `eval`, `exec`, `source`, `.`, `command`, `builtin`, `trap`, `declare`/`export`/`read`/`unset` and every other builtin except `echo`, `printf` (after a fixed format, without `-v`), `cd`, `pushd`, `pwd`, `true`, `false`, `:` and `test`/`[` (right after an operator such as `-f` or `=`, not `-v`); programs whose purpose is to run a command, code, package, container, task or file they are given: wrappers such as `env`, `sudo`, `doas`, `su`, `runuser`, `nohup`, `nice`, `ionice`, `taskset`, `cpulimit`, `timeout`, `time`, `chronic`, `stdbuf`, `setsid`, `chroot`, `flock`, `strace`; watchers `watch`, `watchexec`, `entr` and `nodemon`; `xargs`, `parallel` and `ssh`; `awk` and `sed`; package runners `npx`, `pnpx`, `bunx`, `uvx`, `corepack`, `tsx` and `ts-node`; build and task runners `make`, `just` and `task` (a value could pick the makefile, the target or a variable a recipe expands), and build tools and tool version managers such as `mvn`, `gradle`, `cmake`, `dotnet`, `tox`, `nx`, `mise`, `asdf`, `nvm` and `pyenv`; interpreters and shells such as `sh`/`bash`, `python`, `perl` and `node` (except as described for script interpreters below); and `find … -exec`. Package managers and container tools take a value only in a subcommand on an allowlist of ones that list or describe and run no package, lifecycle or build script, project task, container or plugin: `npm view`/`info`/`show`/`v`/`search`/`find`/`s`/`se`/`ls`/`list`/`la`/`ll`/`outdated`/`explain`/`why`; `pnpm list`/`ls`/`ll`/`la`/`why`/`outdated`; `yarn info`/`why`; `uv pip show`/`list`/`freeze`/`tree`; `pip` (`pip3`, `pip3.12` …) `show`/`list`/`freeze`/`check`; `pipx list`; `poetry show`/`search`; `cargo search`/`tree`/`info`; `go doc`/`list`/`version`; `gem list`/`search`/`info`/`contents`/`dependency`; `bundle list`/`info`; `composer show`/`info`/`search`/`depends`/`why`/`prohibits`/`why-not`/`outdated`/`licenses`; `docker`, `podman` and `nerdctl` `ps`/`images`/`logs`/`inspect`/`top`/`port`/`stats`/`history`/`version`/`info`/`search` and the listing and inspecting subcommands of `container`, `image`, `volume` and `network`; `kubectl get`/`describe`/`logs`/`explain`/`version`/`api-resources`/`api-versions`/`top`/`config view`; `conda`, `mamba` and `micromamba` `list`/`search`/`info`; `apt show`/`search`/`list`/`policy`; `apt-cache show`/`search`/`policy`/`depends`/`rdepends`/`showpkg`; `dnf` and `yum` `info`/`list`/`search`. `bun`, `brew` (which runs a formula's code to describe it), `pdm`, `hatch`, `rye`, `pixi`, `apt-get`, `pacman`, `apk` and `zypper` take none. `npm docs`, `bugs`, `repo` and `help` are left out because they start a browser on an address the package chooses. The subcommand must be fixed words right after the program, and the value an operand after it: not an option or part of one (`--pkg=$1`), not right after an option (`--userconfig "$1"`, `--python "$1"`, `--kubeconfig "$1"` choose code to run), and, unless a `--` comes first, not a value that starts with `-` (that line is not run, with a note). Any other subcommand (`install`, `add`, `ci`, `run`, `exec`, `test`, `build`, `x`, `dlx`, a script name …), a missing or dynamic one, or options before it keep a value off the whole line: `npm install; echo "$1"` does not run either; in PowerShell `&`, `.`, `Invoke-Expression`/`iex`, `Invoke-Command`, `Start-Process`, `Start-Job`, `Add-Type`, `ForEach-Object` and any command after a `-Command`/`-c`/`-EncodedCommand`/`-ScriptBlock` parameter. Path variables the host sets (`${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}`, `${CLAUDE_SKILL_DIR}`, `${CLAUDE_PROJECT_DIR}`) are not your or the model's input, so they may also name the command (in PowerShell after `&`) or an interpreter's script. A script interpreter may receive a value only in its documented script form, `<interpreter> [options] <script> [arguments]`, where the interpreter reads no option after the script and passes every later word to the script as an argument. The script must be a fixed word or a host path variable; the value must come after it. Only these forms count: `node`, with no option but `--no-warnings`, `--no-deprecation`, `--enable-source-maps`, `--trace-warnings` or `--trace-uncaught` (never `node inspect`); `python`, `python3`, `python3.12` and the like or `pypy`, with no option but `-B`, `-E`, `-I`, `-P`, `-q`, `-s`, `-S` or `-u`; `bash`, `sh`, `zsh`, `perl` and `ruby` with no options at all (so perl's and ruby's `-s`, which turn the script's arguments into switches, cannot occur); and bash's `source`/`.` with a fixed file. So `` !`node "${CLAUDE_PLUGIN_ROOT}/scripts/tool.mjs" status "$ARGUMENTS"` `` runs. A value is refused as or before the script, after `-`, `--`, `-e`, `-c`, `-m` or any other option, and anywhere on a line run by any other interpreter, script host or shell: `bun`, `deno`, `irb`, `php`, `lua`, `luajit`, `Rscript`, `R`, `osascript`, `tclsh`, `wish`, `jshell`, `jrunscript`, `groovy`, `java`, `awk` and its kin, `dash`, `ksh`, `mksh`, `fish`, `csh`, `tcsh`, `ash`, `busybox`, `pwsh`, `powershell`, `cmd`, `wscript`, `cscript`, `mshta`, and the Windows programs that start a shell or run what they are given (`wsl`, `wt`, `runas`, `rundll32`, `regsvr32`, `forfiles`, `msiexec`). One counts as such however it is written: with a path, in any case, with a version (`python3.12`, `nodejs22`, `bash5`), a suffix after a version (`python3-dbg`), a Windows extension (`node.cmd`, `C:\tools\node.exe`) or as a Windows variant (`py`, `pyw`, `pythonw`, `javaw`, `rubyw`). A program whose name merely starts like one (`pyright`, `rm`, `shuf`) is an ordinary program. A line that defines a function or alias does not run either, and neither does a line with a value where a program reads code from a stream: a pipeline stage, a `>(…)` process substitution or a program with redirected input that is an interpreter or shell without a fixed script (`echo "$1" | sh`, `| bash -s`, `| python3 -`), `sed`/`awk` with a program file from standard input, any runner above (`| xargs sh -c`, `| ssh host`), a program named at run time (`| $SHELL`), or in PowerShell `Invoke-Expression` and the other runners above except `ForEach-Object` and `Where-Object`; or an interpreter or `source`/`.` whose script is a process substitution (`bash <(…)`, `source <(…)`). A process substitution read as data (`diff <(echo "$1") x`) and a pipeline into a fixed script (`| python3 tool.py`) are fine. For these line checks a wrapper counts as the command it runs: bash's `command [-p]`, `builtin` and `exec [-cl] [-a name]`, and `env`, `nice`, `nohup`, `timeout`, `stdbuf`, `time` and `setsid` with their documented options, so `| command sh` and `| timeout 5 sh` are refused and `| nice wc -l` is fine. A wrapper with any other option (`env -S`, `command -v`), any other wrapper (`sudo`, `doas` and the like) and a program named at run time count as reading code and running a package manager. The program still receives the value as one ordinary argument, so a value starting with `-` may read as an option. A command that writes `'$1'` therefore works in Claude Code but not here; write `"$1"` instead. A value also never reaches code through a file. If any shell line of a command or skill carries an argument, and one of its lines runs a file after another line or command may have written one, none of its shell lines run, and each gets the note "a value could reach code through a file written earlier in this command" (`echo "$1" > x.sh; bash x.sh`, `printf %s "$1" | tee x.py >/dev/null && python3 x.py`, or a write on one line and a run on a later one). Writing means an output redirection to a file (not `/dev/null` or `2>&1`) or `tee`, `cp`, `mv`, `ln`, `install`, `rsync`, `unzip`, `patch`, `wget`, `dd of=`, `sed -i`, `perl -i`, `curl -o`/`-O` or `tar -x` (in PowerShell every redirection above but merges, `$null` and `NUL`, and `Out-File`, `Set-Content`, `Add-Content`, `Tee-Object`, `Copy-Item`, `Move-Item`, `Rename-Item`, `New-Item`, `Expand-Archive`, `Invoke-WebRequest`, `Invoke-RestMethod -OutFile`, `Start-BitsTransfer` and the file-writing `Export-*` cmdlets, with their aliases). Running a file means an interpreter or shell, `source`/`.`/`eval`, a program named by a path (`./x`, `dir/x`) or at run time, a runner, `find -exec`, or a `$(…)`, backtick or `<(…)` substitution. Inside a pipeline, loop, `if`/`case`, group or subshell, and in the background, order counts as unknown, so the run comes after the write. A single command that writes its own output (`node x.js "$1" > out.txt`) is fine. These rules cannot know every program: a program not listed above may still treat an argument as an instruction (for example `git --upload-pack=…`) or write a file in a way the list above does not know. A file written by one run of a command, or by another command or skill, and run later is beyond what one body shows. When the model can choose a skill's or command's arguments, migrate only plugins whose shell lines you are comfortable running with model-chosen values.
- **`@file` stays inside known places.** A reference in the command's or skill's own text attaches a file only from places that template may reach, with symbolic links resolved first. A project's command or skill reaches only the workspace. An installed plugin's reaches its own directory and the workspace. Only your own commands and skills (in `~/.claude`, or roots you configured) also reach `~/.claude`. Anything else is not attached, and a `[Harness Forge: @… was not attached …]` note says so. An `@path` you type in the arguments is plain text; DSH handles your own attachments.
- **Trust is checked on what actually runs.** Each time a project's command or skill is rendered, Harness Forge reads its current text and checks the workspace's trust again. If the workspace is not trusted (or no longer is), none of its shell lines run, even ones added after it was loaded, and a note in their place explains why.

## Models

A `model:` in an agent, skill or command can name a Claude alias (`haiku`, `sonnet`, `opus`, or a `claude-…` id). Model names do not say which DSH model is stronger, so without a `modelAliases` entry ([quick start](quickstart.md#configuration)) the session's model answers it. A skill's `model` or `effort` applies to the turn it runs in and is switched back afterwards.

## Instruction files

DSH's own instruction loader already reads `AGENTS.md`, `CLAUDE.md` and their `.local.md` files from the repository root down to the working directory, so Harness Forge does not add those again. The **Instructions** row adds only what DSH does not read, to the system prompt:

- `~/.claude/CLAUDE.md`, and `.claude/CLAUDE.md` in each directory from the repository root (the nearest `.git`) down to the working directory. Without a repository: up to your home directory when the working directory is inside it, otherwise the working directory alone.
- `@path` imports in those files and in the `CLAUDE.md` / `CLAUDE.local.md` files DSH loads: relative to the importing file, `~/`-relative or absolute; at most 5 levels; each file once; never inside a code block or inline code. Imports in a project's files (every `CLAUDE.md`, `.claude/CLAUDE.md` and `CLAUDE.local.md`) stay inside the workspace: the repository root, or without a repository the working directory, with symbolic links resolved first. Files are still *found* up to your home directory, but a file found above the working directory cannot import from there either, so a cloned repository cannot pull a file like `~/.ssh/id_rsa`, or another project's files, into the prompt. The exception is a workspace whose external imports you approved in Claude Code (`hasClaudeMdExternalIncludesApproved` in `~/.claude.json`); then, as in Claude Code, its imports may point anywhere, `~/.claude` included. Your own `~/.claude/CLAUDE.md` may import from anywhere. A project instruction file that is itself a symbolic link to a file outside the workspace is not read at all.
- Codex's `~/.codex/AGENTS.override.md` (or `AGENTS.md`), unless your Codex setup is migrated and already carries it.

The total is capped at 65536 bytes: the broadest files are left out first, then the most specific one is cut, with a note saying so. Reading is bounded too, because it runs for every workspace, trusted or not: one load reads at most 4 MiB (each file at most 1 MiB, and a binary file's bytes count too) while trying at most 256 paths (an import that does not exist counts too), and lists at most 32 files it did not use. Past a limit it stops, touches no further file, and a note in the prompt and on the workbench names where. Each file is opened once: the check that it lies where it may is made on the opened file's real path, and its text is read from that same open file, so a link swapped in after the check is not followed. When [Recollect](https://github.com/kirkchinese/DSH-Recollect) is installed, the row steps aside entirely. Switch the row off to stop adding instruction files.
