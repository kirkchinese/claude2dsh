# Changelog

All notable changes to Harness Forge are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/).

## Unreleased

Everything since 0.4.0, the version on npm. Plugins can now come straight from the internet, several holes in hooks, permission rules and command shell lines are closed, Discover lists only what each harness really installed, and session import handles large and forked histories.

### Security

- **Migrate all takes only what you installed and switched on (0.4.0 is affected).** It also migrated every plugin that a locally cloned Claude Code marketplace offered, and plugins switched off in their harness, starting their MCP servers and hooks. Discover now lists only installed plugins; ones switched off in Claude Code, Codex or OpenCode (`-<id>`, `*` and later entries in `plugins`) stay listed, marked off, and are left out of **Migrate all**, but can still be migrated one by one. Plugins an earlier version migrated this way stop running after the upgrade and are marked in **Migrated**, where you keep or remove them.
- **A plugin removed or switched off in its harness stops running in DSH (0.4.0 is affected).** A migrated Claude Code, Codex or OpenCode plugin that its harness uninstalled or switched off kept running. Its parts are now withdrawn, and **Migrated** offers **Keep** (a local copy that no longer follows the harness) or **Remove**. This happens only after the harness's plugin list was read in full: a list caught mid-write or malformed changes nothing, and **Diagnostics** names it until it reads again.
- **A hook condition could freeze DSH (0.4.0 is affected).** Checking a hook's `if: Bash(…)` rule against a command that starts with an assignment not followed by a space (for example `ROOT=/some/path && echo x`) took exponential time, and DSH stopped responding at 100% CPU. The command is now read in a single pass, and other patterns that read text from plugins, models or the network (source addresses, the hook model's answer, `.mcp.json` variables, URLs in error text) were rewritten the same way.
- **Wildcards are matched within a budget (0.4.0 is affected).** Wildcards in permission rules and hook conditions used to become regular expressions that could backtrack on many `*`. They are now matched in time proportional to the text times the pattern. A pattern longer than 1,000 characters, a text longer than 100,000 characters, or a match needing more than 4,000,000 steps is not matched: deny and ask rules then apply and a hook's `if` lets the hook run, while allow rules do not approve.
- **Values in command and skill shell lines are refused on lines that run code (0.4.0 is affected).** An argument such as `$ARGUMENTS` is no longer placed on a line run by a package, container, task or wrapping runner (`npx`, `npm exec`, `pnpm dlx`, `uvx`, `pipx run`, `docker run`, `kubectl exec`, `make`, `just`, `watchexec`, `taskset` and the like), or by a Windows launcher that starts a shell or runs what it is given (`wsl`, `runas`, `rundll32`, `msiexec`…). Interpreters, script hosts and shells are recognised however they are spelled (`python3.12`, `pythonw`, `node.cmd`, `C:\tools\node.exe`). A package manager takes a value only as an operand of a subcommand that runs no package or project code (`npm view`, `pip show`, `cargo search`…); `npm install "$1"` and the like are refused. A line where a program reads code from a pipe, standard input or a process substitution, such as `echo "$1" | sh` or `echo "$1" | command sh`, is refused too; wrappers such as `command`, `exec`, `env` and `timeout` are seen through. A command or skill whose shell lines carry a value runs none of them when one line may write a file and a later one runs a file (`echo "$1" > x.sh` then `bash x.sh`).
- **`WebFetch(domain:…)` deny and ask rules match (0.4.0 is affected).** They were read as a rule on an input parameter named `domain`, which a fetch never has, so they never matched.
- **Shell spelling no longer slips past Bash rules (0.4.0 is affected).** A rule and a command are compared as the words the shell reads, so extra spaces, quotes and backslashes (`cat  'secret.txt'`) no longer avoid `Bash(cat secret.txt)`. Redirections are set apart, so `git status > out` still meets a rule for `git status`; as in Claude Code, an allow rule approves the command, a file it writes needs an `Edit` allow rule, and a file it reads outside the working directory a `Read` allow rule. Each such file gets the same deny, ask and allow rules as a direct read or edit, and the null device (`/dev/null`, `$null`, `NUL`) is no file. `PowerShell(…)` rules work the same way: they compare words, without case, with every PowerShell redirection (`*>`, `2>&1`…) set apart, and they match PowerShell's default aliases as their cmdlets (`rm` and `del` meet a rule for `Remove-Item`), as in Claude Code; an allow rule approves an alias only on a platform that defines it. A trailing `&` (a background job) ends a command, so `rm x &` still meets a rule for `Remove-Item`, and a quoted `'$null'` is a file, not the null device. A command whose syntax cannot be read matches deny and ask rules.
- **File rules are anchored as in Claude Code (0.4.0 is affected).** `//path` is absolute, `~/path` is under your home folder, `/path` is under the folder of the settings file that defines the rule (it was the working directory), and a relative path is under the working directory (`./x` is exactly that file, as in gitignore); a rule never matches a file outside its anchor. A symbolic link is checked both as written and where it leads, also when it leads to a file that does not exist yet: deny and ask rules match either, and an allow rule (or the working directory's own exemption) must cover both; a link loop counts as unknown. A rule's own folders are resolved the same way, so `Read(//etc/hosts)` still covers macOS's `/private/etc/hosts`, and on Windows paths compare without case and with either separator. A deny or ask rule that names a folder (`Read(secrets)`) now also covers everything inside it, and `dir/**` matches that folder at any depth.
- **A plugin's MCP server marked `enabled: false` is not started (0.4.0 is affected).** Its part says "disabled in the plugin". This holds for Claude Code and Codex plugins alike.
- **Harness Forge never reaches out to a network share on Windows (0.4.0 is affected).** Reading a path such as `//server/share/…`, or a link to one, makes Windows sign in to that server with your credentials. Permission checks, instruction-file imports, `@file` attachments, OpenCode plugin entries, the scanning of plugin and project folders, and paths a plugin, project or Git file names (package entries, worktree links, MCP programs and working directories, watched files) no longer touch a share the workspace or configuration is not on, directly or through a link; such a path counts as unknown (deny and ask rules apply, allow rules do not) or is skipped with a note.
- **Importing a very large session no longer takes the DSH server's memory (0.4.0 is affected).** Sessions were read whole into memory; Claude Code, Codex and OpenCode sessions are now streamed record by record. A session above 100 MB is refused, in your language: a plain file before it is read, with its size; a compressed `.jsonl.zst` rollout while it is decompressed, as soon as its decoded size passes 100 MB. **Import sessions** greys out a session that is too large by the size it can see beforehand, which for a compressed rollout is its size on disk.

### Added

- **Get plugins.** On the Discover screen, **Get plugins** takes a Claude Code or Codex marketplace (`owner/repo`, a git URL or a `marketplace.json` URL), a single plugin repository or subfolder, or an OpenCode npm package. Anthropic's official, community, skills and knowledge-work marketplaces and OpenAI's curated Codex plugins are listed ready to open, and each is fetched only when you open it. You don't need the original harness. Marketplaces already on this computer are under **On this computer**.
- **A confirmation before anything is installed.** It shows the source (with a link when it is on the network), the exact commit or version (and the npm registry), every part with whether it works in DSH and why not in your language, and each part that runs code (hook events, MCP server commands, shell lines, scripts, code plugins) with whether it runs in DSH once installed or is a gap that runs nothing until you build an adapter. Nothing fetched runs before you confirm, and what is installed is exactly what was shown: if the files change in between, the install is refused. A plugin from a marketplace on this computer is copied when its confirmation opens, leaving out links and special files, and only that copy is shown and installed.
- **Downloads stay in Harness Forge's own folder** (`<profile>/.harness-forge/data/remote/`), never in `~/.claude`, `~/.codex` or OpenCode's configuration. git fetches only the pinned commit, without your git configuration, hooks or credential helpers; without git, GitHub repositories are downloaded over HTTPS. An npm package's tarball is checked against its integrity before you confirm, and its dependencies are then installed from the registry only, without install scripts, from a version 3 lockfile that is audited. Archives with links or special files are refused, and cancelling stops the download and the unpacking.
- **Network limits.** A marketplace may name only public HTTPS sources, never this computer or your local network. `HTTPS_PROXY`, `HTTP_PROXY` and `ALL_PROXY` (minus `NO_PROXY`) are honoured; through a proxy, Harness Forge itself reaches only GitHub, npm's registry or yours, and the hosts you paste. Once you confirm an npm package, npm installs its dependencies and may contact other hosts the registry names. Every operation is bounded in size and time, and network failures, including GitHub's rate limit, are reported in plain words.
- **Check for updates and Update.** They compare each plugin's commit or npm version with its source. An update is confirmed like an install, showing the new revision and which parts are new or changed, and keeps the parts you switched off. It is refused if another installation replaced that plugin after the check.
- **Marketplace entry sources.** Every source Claude Code documents except `command`: relative paths (also bare names under `metadata.pluginRoot`), `github`, `url`, `git-subdir` (with `owner/repo` shorthand), `npm` and `archive`. An entry also acts as the plugin's manifest, following Claude Code's `strict` rules.
- **Plugins from Get plugins in the workbench.** They are grouped under "Installed through Get plugins", each with its source (an address, or "local marketplace: <name>"), and shown in **Migrated**, not in the Claude Code, Codex or OpenCode sections. A plugin keeps its own name everywhere; two that share one are shown as `name (claude-code)` or `name (network)`. Removing one deletes its downloaded files, and the Remove dialog says so.
- **dsh-chat-import is recommended for session import.** The first-run banner and **More → Import sessions** offer [dsh-chat-import](https://github.com/Nwflower/dsh-chat-import) (Claude Code, Codex, OpenCode and 40+ other agents) with **Install**, which asks first and installs it through DSH's plugin manager. While it is installed, Harness Forge's own import steps aside and points to its **Import sessions** button in the sidebar.
- **Compressed Codex rollouts.** `rollout-*.jsonl.zst` files (Codex 0.167+) and archived sessions are found and imported.
- **Applying migrated plugins.** After DSH starts, Discover and **Migrated** show "Applying migrated plugins: N of M done…" until every migrated plugin is applied again.
- **Easier to read and to share.** The page shows paths under your home folder as `~/…`, so a screenshot does not show your user name; actions still use the full path. After a migration it says when a SessionStart hook takes effect only in new sessions, and its More, Back and Close buttons have names of their own for screen readers.
- **Chinese detail page.** With DSH in Chinese, Harness Forge's page in **Plugins** shows a Chinese description instead of the English README.

### Changed

- **Claude Code and Codex installs are read as those harnesses read them.** Claude Code plugins come from `installed_plugins.json`, the newest user-scope install each; installs for one project (`--scope project`, `--scope local`) are left out of the global list and no longer replace the user-scope one. Whether one is on follows `enabledPlugins` in your user settings, then the managed settings. Codex plugins come from `config.toml` `[plugins]`, one cached version each, and are always listed under Codex, even when they also carry a Claude Code manifest.
- **OpenCode discovery follows OpenCode.** It finds `.ts`, `.js` and `.mjs` plugin files and package folders right inside `plugins/` (or `plugin/`), and the packages `opencode.json(c)` configures: local folders, and npm packages installed in the config folder or OpenCode's cache. Control entries (`-<id>`, `*`, `<prefix>.*`) switch plugins off and on in order, global config before the project's, as OpenCode does. A plugin's id is read from its one `Plugin.define({ id })`, with escapes decoded as JavaScript does, never from a comment or a string; when it cannot be told and an entry could switch the plugin, the plugin is shown as maybe off, with the reason, and left out of **Migrate all**. An entry that cannot be resolved, or a harness record that cannot be read, is skipped and named in **Settings** instead of hiding every harness's plugins.
- **Discover reads only the harnesses' folders.** It no longer also searches the folder DSH was started in, which listed unrelated folders and was slow from the home folder. A workspace's own `.claude/` is still read for its sessions.
- **The official Codex plugin's commands run.** A line such as `` !`node "${CLAUDE_PLUGIN_ROOT}/scripts/codex-companion.mjs" status "$ARGUMENTS"` `` was refused because `node` runs what it is given. A path variable the host sets may now name a command or a script, and a value may follow the script in the documented script form of `node`, `python`/`pypy`, `bash`, `sh`, `zsh`, `perl` and `ruby`, with a short list of harmless options (none for the shells, Perl and Ruby). Every other interpreter, script host or shell takes no value anywhere on its line.
- **Codex MCP settings are honoured.** Servers from `config.toml` and from Codex plugins are read alike: `env_vars`, headers, `cwd`, `type = "http"`, `enabled_tools`/`disabled_tools`, approval modes (`prompt` and `writes` ask before a call), the tool timeout, and the startup timeout of stdio servers. A stdio server mounted directly still lists filtered tools but refuses calls to them. Codex plugin servers get `CODEX_HOME` and `CODEX_MCP_NODE_PATH` (DSH's Node.js) when their settings ask; a server whose command needs a variable nothing sets is not started, and its part says which. Servers with `auth = "chatgpt"` are not started: they need a ChatGPT sign-in that DSH cannot provide, and are reported as a gap. See [MCP server settings](docs/user/compatibility.md#mcp-server-settings).
- **MCP server names never contain `__`.** A server whose name has `__` gets a single `_` and a short hash in its tool names (for example `mcp__app_reports_4880b6d7__…`), so a tool name always shows which server it belongs to. Permission rules written for such a server's tools need the new name.
- **Instruction-file reading is bounded.** One load tries at most 256 paths (missing ones included), reads at most 4 MiB (binary files included) and names at most 32 skipped files, then stops with a note in the prompt and the workbench and touches no more files. Each file is opened once, as a regular file whose real path was checked, and read from that open file (on macOS and Windows with the limit described in the compatibility notes).
- **Codex and OpenCode imports get their own ids** (`codex-…`, `opencode-…`), so other importers no longer take them for native DSH sessions. Sessions imported by 0.4.0 under the source's id are found and reused, and stay listed even when the list now leaves their thread out (a Codex subagent thread); **Open session** makes such a session known to DSH again and takes it out of the archive if you archived it. A Codex fork, which 0.4.0 imported under its parent's id, now has its own. A session stored under such an id is reused when its creation time matches and, if several threads could be stored there, when this thread alone matches it in every prompt and answer; a thread that differs is imported as new, and when that cannot decide, the row offers **Open existing** and **Import as new**.
- **The import lists show every session, newest first, a page at a time.** Codex rows show the thread name from `~/.codex/session_index.jsonl`, else the first thing you said, and the imported session gets the same title, shortened like other session titles. A thread Codex continued in other files is one row; forks stay their own and subagent threads are not listed. Claude Code rows show the `/rename` name, else the generated title, the latest summary or your first message. A session without any shows "Untitled session", and **Show more** loads the next page.
- **Imported sessions are recognised after a reload.** The list asks DSH which sessions it already holds, so **Open session** shows for them, and importing one again opens it instead of failing with "already exists".
- **Fill with AI.** The creation agent asks its questions from the brief before reading any files, starts in `~/dsh-adapters` (so writing the adapter does not ask for approval in Workspace Write mode), and reports as soon as `harness_verify_port` confirms the adapter. Its session is grouped in a workspace named after that folder. The brief now forbids reading DSH's token, logs, `/proc` or other processes' files; the agent checks a page through DSH's runtime inspection or asks you to look. It names the current profile and DSH home, and an adapter must find DSH's data at run time and read no other profile; `harness_verify_port` fails one that hard-codes `~/.dsh` or lists the profiles.

### Fixed

- **A migrated plugin follows its harness's updates (0.4.0 is affected).** When Claude Code or Codex updated a plugin into a new version folder, the migrated plugin kept pointing at the old, often deleted, folder and showed as ready with no parts, and Discover did not offer the new version. It now moves to the new version by itself, keeps the parts you switched off, and says "Updated by Codex from … to …". A migrated plugin whose folder is gone shows every part as an error saying so.
- **Codex `mcp_tool` hooks reach their server (0.4.0 is affected).** They named the tool differently from the MCP row and failed with "not connected"; they now find their server by the name the plugin declared (such as `cua_repl`) and reach it directly or through the capability catalog, and, as in Codex, obey the server's tool filters without asking for approval.
- **Hooks read their input from a file (0.4.0 is affected).** A hook that read stdin synchronously, like the Codex plugin's SessionStart, SessionEnd and Stop hooks, could fail with `EAGAIN: resource temporarily unavailable` when DSH was busy. Stdin is now a file in a private folder of Harness Forge's data folder: on Linux and macOS only you can read it; on Windows it takes the access rights of that folder in your profile. It is removed once the hook has it, a file that cannot be removed is reported in **Diagnostics**, and when no such file can be made the input goes through a pipe as before.
- **A Bash deny rule of several words no longer refuses every command with a `$` (0.4.0 is affected).** With `Bash(cat secret.txt)` denied, `echo $HOME` was refused. Such a command now matches a deny or ask rule (or a hook's `if`) only when its words before the first expansion agree with the rule's: `cat $F` and `cat secret.txt $X` are still denied, `echo $HOME` is not. Allow rules still never approve a command that expands something.
- **Switching the Agents row off and on works (0.4.0 is affected).** Its agents showed "failed to switch off: cannot create effect on inactive context", and afterwards only one agent was offered until DSH restarted.
- **OpenCode plugin commands come back (0.4.0 is affected).** Commands a plugin added return when the commands row is switched on again after the plugin started.
- **A failed MCP server is retried only when the MCP row starts again (0.4.0 is affected),** not once for every other part of Harness Forge that starts.
- **Revoking trust withdraws what is left (0.4.0 is affected).** Parts of an ended session whose withdrawal failed are withdrawn again on every trust change, without being mounted again.
- **The ledger no longer loses records (0.4.0 is affected).** A record that failed validation was dropped without a word and the loss written back at the next change, and a ledger written by a newer Harness Forge was replaced by an empty one. Now a ledger that needs repair is first kept as `state.json.unreadable-<time>`, repairable records are repaired, the rest are reported in **Diagnostics**, and a newer version's ledger is only read, never written.
- **Migrate all works in the Agent Skills section (0.4.0 is affected).** It migrated nothing there, because the section's harness was read as Claude Code.
- **Codex's global instructions and `notify` count as working (0.4.0 is affected).** `~/.codex/AGENTS.md` was marked as having no DSH equivalent, although Harness Forge adds it to the system prompt.
- **A skills folder with a skill called `agents`, `commands` or `hooks` is still Agent Skills (0.4.0 is affected).** It no longer makes the whole folder look like a Claude Code plugin.
- **Claude hooks read the same instruction files as the prompt (0.4.0 is affected).** The `prompt.context` hook stopped reading every `CLAUDE.md` up to the filesystem root; it now stops at the repository root (or the working directory outside a repository), and its `@import`s follow the same rules as the prompt's.
- **The overview counts an adapter only when it runs (0.4.0 is affected).** An adapter whose plugin row failed to start no longer counts as covering a part in the overview, as `harness_verify_port` already required.
- **One status line, one gap (0.4.0 is affected).** A `statusLine` in `~/.claude/settings.json` that runs a plugin's own script is shown as part of that plugin (for example claude-hud), not as a second gap under your settings.
- **Imported sessions open at once (0.4.0 is affected).** An imported session shows in the sidebar with its title, under its project's workspace, and **Open session** works right away instead of failing with `sessions.retain: unknown session` until DSH restarts. A session from the home folder or a system temporary folder gets no workspace.
- **Imported sessions can be continued (0.4.0 is affected).** Assistant text that came after a tool call (Codex, OpenCode) goes into the next step, so the first new message no longer fails with HTTP 400. Codex tool output wrapped as `{"output": …, "metadata": …}` imports as its output text.
- **Importing one OpenCode session no longer marks every OpenCode row as imported (0.4.0 is affected).**
- **Every workbench answer reaches the browser (0.4.0 is affected).** DSH's Remote channel refuses answers with empty fields, so some actions failed, such as adding an already-installed plugin again by path.
- **Diagnostics tell the truth (0.4.0 is affected).** They no longer say "Every part started normally" above failed parts, show Harness Forge's version instead of "Unknown", and name a failed part readably ("claude-hud · Hooks (inline): Interrupt, SubagentStop, Stop") with its real error below.
- **One notice when the workbench row is off (0.4.0 is affected).** The Harness Forge page says "“Harness Forge page” is turned off. Turn it on in Plugins." instead of showing screens where every action fails.

### Removed

- **Browse a marketplace** on the Discover screen, and the workbench calls `marketplaceScan` and `marketplaceInstall` that installed a plugin from a local marketplace in one step. Marketplaces on this computer are under **Get plugins** → **On this computer**, where every install goes through the confirmation.

## 0.4.0 - 2026-11-27

The first public release under the Harness Forge name: a smaller product, built around switchable rows, a new workbench, and DSH's own creation mode for the parts DSH cannot run.

### Changed

- **Safer command and skill rendering.** Shell lines and `@file` references are found in the command or skill text before any argument goes in. Arguments inside a shell line reach the shell as quoted environment variables. `@file` attaches only files inside the plugin, the workspace or `~/.claude`.
- **Instruction imports stay in the workspace.** A project's `CLAUDE.md` files import only from inside the repository (or the working directory outside one), unless you approved external imports in Claude Code.
- **New package names.** `@kirkchinese/dsh-harness-compat` is now `@kirkchinese/harness-forge`, and `@kirkchinese/dsh-harness-compat-core` is now `@kirkchinese/harness-forge-core`. The old packages and `@kirkchinese/dsh-claude-suite` are deprecated.
- **One package, several rows.** Skills, commands, agents, hooks, MCP servers, Claude Code mods, OpenCode plugins, instructions, sessions, porting and the workbench are separate plugin rows of the one package. Each can be switched off in DSH's **Plugins** page; a row that fails to start is recorded and the others keep running.
- **New workbench.** **Harness** in the sidebar now has three screens: **Discover & migrate** (with marketplace browsing), **Migrated** (switch single parts off, undo) and **Gaps** (reasons and **Fill with AI**), plus **Import sessions**, **Settings** and **Diagnostics**. It follows DSH's language (English or Chinese).
- **Fill with AI uses DSH's creation mode.** For a part DSH cannot run, Harness Forge writes a task brief and opens a session on DSH's `cordis` agent preset, which builds, installs and checks a local adapter plugin `dsh-adapter-<plugin>-<part>`. Publishing is optional and under your own npm scope.
- Requires DSH 0.2.2-rc.3 or later. Tested on DSH 0.2.2-rc.3 and 0.2.2-rc.5.

### Added

- **Workspace trust.** A project's hooks, MCP servers, shell-line commands and skills, and settings that grant tools or set `env` wait until you trust the workspace. A workspace counts as trusted when you accepted Claude Code's trust dialog for it, Codex marks it trusted, or you trust it with the banner on the Discover and Migrated screens. Project `.mcp.json` servers also follow Claude Code's approvals. See [Compatibility](docs/user/compatibility.md#workspace-trust).
- **Instruction files.** The Instructions row adds the Claude Code instruction files DSH does not read itself (`~/.claude/CLAUDE.md`, `.claude/CLAUDE.md`, `@path` imports) and Codex's global `AGENTS.md` to the system prompt. It steps aside when the Recollect plugin is installed.
- **Diagnostics** screen: row faults, failed mounts, the hook shell, Bun and versions.

### Removed

- The suite package `@kirkchinese/dsh-claude-suite`. The capability catalog and Recollect are separate, optional plugins; Harness Forge works with them when they are installed.
- The Recollect toggle in the workbench settings.
- The porting studio templates and its tools, replaced by **Fill with AI** through DSH's creation mode.
- Hosted runs of the Claude Code, Codex and OpenCode command-line tools.
- Repair of sessions imported before 0.3 (`/harness repair-sessions` and the `harness-forge-repair-sessions` command).
- Support for DSH 0.2.1.

### Upgrading from `@kirkchinese/dsh-harness-compat` or the suite

```sh
dsh plugin --profile web remove @kirkchinese/dsh-harness-compat   # or @kirkchinese/dsh-claude-suite
dsh plugin --profile web add @kirkchinese/harness-forge
```

`web` is the main profile that `dsh web` runs; use another profile's name to upgrade that one.

Your migrations are kept: Harness Forge 0.4.0 reads the same ledger (`<profile>/.harness-forge/state.json`). If you used the suite and want the capability catalog or Recollect, install `@kirkchinese/dsh-capability-catalog` or `@kirkchinese/dsh-recollect` on their own. Sessions imported before 0.3 that still need repair must be repaired with Harness Forge 0.3 before upgrading.
